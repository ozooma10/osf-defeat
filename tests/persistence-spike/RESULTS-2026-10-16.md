## Findings and next work

1. **Raw dynamic FormIDs are not a stable cross-process identity oracle.**
   The saved integer IDs differed from the references resolved by the aliases after
   restarting. No second `Begin` was called, and the inventories and pack position
   remained intact. The generated origin cell's ID changed too. Retain raw IDs as
   diagnostics, but replace equality against saved integers with an identity check
   that survives save/load remapping without adding another persistence holder.
   The origin-cell and ship-marker checks, and `Cleanup`'s ownership guard, need the
   same audit. Do not simply refresh expected IDs on load, which would hide replacement.

   | Reference | Before restart | After restart |
   | --- | --- | --- |
   | Authored subject | `FF023259` | `FF019A96` |
   | Authored pack | `FF02325C` | `FF019A97` |
   | Generated subject | `FF02413D` | `FF01B438` |
   | Generated pack | `FF024140` | `FF01B439` |
   | Generated player/origin cell | `FF01D33A` | `FF01D2AE` |

2. **Departure diagnostics conflate a missing cell with an attached cell.**
   The authored run traveled through the normal map from New Atlantis to Gagarin,
   then landed at a Rocky Desert site. `MarkAway` reported
   `Original cell has not been observed detached` at 16:01:31 and again at 16:02:17
   after saving/reloading there. That message covers both `origin == None` and
   `origin.IsAttached()`, so it cannot identify the cause. Split those observations,
   log alias cells and loaded-3D state independently, and correct cell resolution
   before rerunning. No return or elapsed-time pass is claimed.

3. **The objective name is visibly unresolved.** Both journals displayed
   `Inspect [...] after returning to the original site`. The generated run requested
   `SetOverrideName` at 16:08:58; the journal still showed the placeholder after
   reloading the override save. Investigate alias text storage/fill timing and the
   actual actor name separately; changing the name request alone is not verification.

4. **A known landed-ship interior marker works in this layout.** Both profiles used
   the same Frontier home ship (`260072`) and interior (`84934966`). Each run captured
   a clear hab-floor marker, exited through the hatch, saved outside, called `TestShip`,
   walked and looked around, and exited through the hatch again. Reloading the outside
   save and repeating also passed. This proves the narrow captured-marker operation;
   it does not prove automatic safe-marker discovery, other layouts, cold-restarted
   marker identity, orbit/docking behavior, or ship-domain defeat.

Next: repair the probe's identity/cell observations and alias text, rebuild into fresh
private profiles using these same clean seeds, then rerun cold restart, normal departure,
away-save/reload, exact-site return, and the recorded 48-hour repeat. Keep Minimal Shadows
gated until those results and actual actor names are verified.
